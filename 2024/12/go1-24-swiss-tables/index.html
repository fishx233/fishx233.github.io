Go1.24 map实现：Swiss Tables
2024-12|Go源码分析

本文基于Go1.24rc1，1.24发布后可能有变更。

Swiss Tables

概述

Swiss Table是由Google工程师于2017年开发的一种高效哈希表实现，并在2017年CppCon大会上详细介绍了他的工作原理，旨在优化内存使用和提升性能，解决Google内部代码库中广泛使用的std::unordered_map所面临的性能问题。（Rust的Map也是基于swiss table） 其核心为充分利用了SIMD指令及L1缓存。

SIMD

SIMD是Swiss Table进行快速比对的核心部分。

单指令流多数据流（英语：Single Instruction Multiple Data，缩写：SIMD）是一种采用一个控制器来控制多个处理器，同时对一组数据（又称“数据向量”）中的每一个分别执行相同的操作从而实现空间上的并行性的技术。

数据分布

在Swiss中，哈希函数的结果产生一个64位哈希值。我们将该值分成两部分： H1，为前57位哈希值，用于标识group的索引，该索引像任何普通哈希值一样用于查找和插入。 H2，为后7位哈希值，用于存储此元素的元数据。H2哈希位单独存储在表的元数据部分中。

Swiss 表的元数据存储状态信息（例如该slot是空的、已删除的还是已满的）。每个元数据条目由一个字节组成，该字节由一个控制位和7位H2哈希组成。控制位与元数据H2部分中的值相结合，来标识相关slot是空的、已存在元素还是已删除的。 状态分别为：

hash冲突

Swiss table使用开放地址法来解决hash冲突。在Go中主要采用二次探测

每个group包含8个槽位。查找时，先根据H1确定起始group，再通过H2筛选该group中的候选槽位，并比较完整key。如果未找到目标key且group中存在空槽，则结束查找；如果没有空槽，则继续检查探测序列中的下一个group。每次跳转的步长依次为1、2、3……，超出group数量时取模。已删除槽位的墓碑标记不会终止探测。

查找过程

在表中搜索项目时，我们使用SIMD 指令扫描候选匹配项。查找元素的过程可以粗略概括如下：

  1. 使用 H1 哈希来找到该哈希的“存储桶链”的起点。
  2. 使用 H2 哈希构造一个掩码。
  3. 使用 SIMD 指令和掩码生成一组候选匹配。
  4. 对每个候选进行检查。
  5. 如果在当前候选中未找到任何元素，则执行探测以生成一组新的候选。请注意，删除的元素不会停止探测，但空元素会停止探测。

Go中的实现

数据结构

这是map类型结构，包含一些类型信息和大小信息，Golang会通过类型结合运行时来生成对应的map类型，跟原来的map差不多。

为了实现渐进式扩容，Go将map分成了多个table，以防止扩容时带来的时延过高（以前的map支持渐进式扩容需要保证兼容性）。

dirPtr和dirLen则分别表示指向的table数组和指向table目录大小, 其大小为2globalDepth，globalDepth和globalShift则是用来计算数据在哪个table时用到的，分别表示**表索引使用的位数和移动位数**，在64位系统globalShift=64-globalDepth。例如有2个table，则globalDepth=1，globalShift=63。（table的数量为2n，一方面是为了快速求余，另一方面是为了使用动态哈希技术，方便渐进式扩容，比如：初始可能只用1位哈希值来区分，需要时可以扩展到用2位，再需要时可以扩展到用3位，以此类推。）

从常量maxTableCapacity可以看出来table目前最大容量为1024。

table中的groups指向groupsReference，而groupsReference中的data指向groupReference。

初始化

Go对小元素map做了优化，如果创建时如果容量大小小于8个，会直接返回map，不进行内存初始化，因为小于8个元素一个Group就够了，当第一个元素被添加到空 map 时，它会分配一个 8 槽位的组。因此，在 map 创建期间预先分配这个组没有好处。实现选择推迟分配内存，直到实际需要时 (即添加第一个元素时) 才进行分配内存。这会在创建了 map 但未使用的情况下节省内存。

如果元素个数<8，则dirPtr不再指向table，而是直接使用group结构来承接（group大小就是8刚刚好）这步操作实际是在set时执行的，具体可以看存储过程中的代码。

查找

方法签名都跟原先的map类似，分为了runtime_mapaccess1和runtime_mapaccess2，对应了是否返回ok，我们看一个mapaccess1即可。

查找步骤为：

  1. 计算hash值。
  2. 计算table索引, 获取对应的map。
  3. 根据h1获取到对应group。
  4. 遍历group中的slot，匹配h2，找到匹配的key 。
  5. 直到遍历到空slot，如果没有找到，找到则返回对应值，返回零值。

针对小于8个元素的map，会直接调用getWithKeySmall来查找。

删除

删除的逻辑比较简单，直接将对应的key设置为deleted即可，删除的逻辑跟查找类似，先找到对应的table，再找到对应的group，再找到对应的slot，最后将对应的slot设置为deleted即可。 就不重复赘述，只看一段逻辑：

进行删除时，如果该group有空slot，此时直接将该slot设置为空即可，如果该group已经满了，则需要设置为已删除标志，即为墓碑，因为如果slot已满的情况，在开放地址法的情况下，可能元素会插入在下一个group，不能直接将该元素删除，否则查找的时候，不会继续往下一个slot查找。

扩容

容量x2，遍历所有旧table的元素，然后在新table上执行put操作，然后替换旧的table。

这里使用了动态哈希的技术，将表分割为两个之后，其数据只会落在指定的两个table中，例如目前mask是两位，扩展到三位，目前table中的值只会落在两个table中。例如hash值为010xxx，011xxx，mask取最高2位时，都落在该table中，扩到3位后，第三位为0的落在i2中，而第三位为1的，落在i2+1中。

性能对比

基准测试（（缺少一些优化，仍然可以看出效果）

  • 大型 (>1024 个条目) Map的访问和分配改进了约 30%。小型Map的访问在某些情况下会出现轻微的倒退。
  • 分配到预先调整大小的Map中的效果提高了约 35%。
  • 整体迭代速度加快约 10%，对于低负载（大尺寸、少数条目）的Map，迭代速度加快约 60%。
  • Sweet中的应用基准测试速度通过几何平均值提高了约 1.5%。

总结

  1. 看完实现其实可以发现，Map仍然没有实现缩容的功能，所以如果Map大量扩容之后，没有回收，仍然有可能造成内存泄漏。
  2. 在现阶段更多的优化与计算机底层相结合，例如simd的特性也衍生出了很多独特的算法来更好的使用这个能力，以及各种压榨cpu三级缓存的技巧，都让了看了直拍大腿，妙啊！也证明了基础扎实的重要性！
